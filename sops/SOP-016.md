# Huey simulations: test an agent by running synthetic conversations against it

Huey is the owner's agent-testing platform. It is on the MCP server **huey** (`use_mcp_tool` with `server: "huey"`). Its tools: huey_whoami, huey_list_resources, huey_get_resource, huey_onboard_agent, huey_manage_project, huey_manage_campaign, huey_manage_segments, huey_generate_segments, huey_manage_workforce, huey_run, huey_get_results, huey_get_transcript, huey_manage_report, huey_manage_rubric, huey_review_conversations, huey_guide, huey_delete_resource, huey_admin, huey_settings. Call `list_mcp_tools { server: "huey" }` once if you need an argument schema; `huey_guide { topic: "workflow" }` has the full walkthrough.

## Vocabulary
- **Agent** = the system under test (a Cognigy bot, an ElevenLabs agent, a phone IVR, a web chat). It has `endpoints[]` (channels).
- **Project** = a bundle of test work; new things land in the ACTIVE project.
- **Campaign** = a test suite bound to ONE agent endpoint + a Runner huey + a Monitor huey.
- **Segment** = one test case in a campaign. A **run** = one execution of a campaign or a segment.
- **Huey** (worker) = the synthetic caller (Runner) or scorer (Monitor). **Persona** = the character a Runner plays.

## "Run a simulation" / "test my agent" — do it this way
1. Resolve WHAT to run: `huey_list_resources { resourceType: "campaign" }` (and `"agent"` / `"project"` when needed). Match the owner's words to ONE campaign or segment by name. If two could fit, read the candidates back and ask which — never guess, a run places real calls to the agent and spends credits.
2. Say in one line what you are about to run ("the Sunny booking campaign, 4 segments") and start it: `huey_run { action: "start", target: "campaign" | "segment", ... }` with the ids from step 1.
3. Runs are asynchronous and take 1–5 minutes (voice longer). NEVER wait inside a live call: on a call, start it as a background task (`create_task`) and tell the owner the result will land in the Async thread; in a task thread, poll `huey_run { action: "status" }` every 30–60 s until finished.
4. Results: `huey_get_results` (default summary). Report pass/fail counts and the one or two most important failures in plain words. Only pull `huey_get_transcript` for FAILING runs, and only a window at a time.
5. Offer the next step once: a report (`huey_manage_report { action: "generate" }`, then `get` until completed, then `get_content`), a rerun, or a look at a failing transcript.

## Other asks
- "What's in Huey?" / "which campaigns / agents / projects do I have?" → `huey_list_resources`, read the names back; no run.
- "How did the last run go?" → `huey_get_results` for the latest run of that campaign.
- Onboarding a new agent from a spec or a website → `huey_onboard_agent` with `dryRun: true` first, read the plan back, then `dryRun: false` only when the owner says go.
- New test cases → `huey_generate_segments { mode: "ai_segments", campaignPurpose: <the owner's requirements> }`, read the drafts back, then `huey_manage_segments` to create the ones they want.

## Never
- Never start a run the owner did not ask for, never start the same run twice while one is in flight, never delete anything (`huey_delete_resource`) without reading back exactly what will go and getting a yes.
- Never paste API keys or credentials into Huey arguments or into your replies. Huey redacts secrets in what it returns.
- Never report a result you have not fetched: "it's running" until `huey_get_results` says otherwise.
